# Плейбук: реализация агентом + субагентами за одну сессию

> Назначение: чтобы одна сессия агента доходила от заказа до **закоммиченного, проверенного
> результата** — без «зелёно по памяти», без брошенных детей, без красного репо на выходе.
> Документ универсальный; все примеры взяты из работы над Neuro Property Trade (NPT) 2026-10-16
> и помечены как примеры, а не как обязательства другого проекта.

---

## 0. Что считается результатом сессии

Сессия — это **одна законченная работа**, а не «начал и остановился на лимите». Результат =
набор локальных коммитов + отчёт, где на каждое утверждение есть **строка вывода команды**.
Три исхода сессии допустимы: (1) заказ сделан и проверен; (2) заказ сделан частично и честно
обозначено, что осталось; (3) заказ не сделан — названа причина и что мешает. Недопустим один:
«сделано» без доказательств.

---

## 1. Роли и потоки

**Родитель (оркестратор) держит критический путь.** Он один:
- принимает решения и меняет план по ходу;
- делает коммиты (ребёнок не может «закрыть» работу);
- прогоняет негативные проверки;
- разговаривает с владельцем;
- ведёт todo-список сессии и бюджет итераций.

**Дети (субагенты, максимум 2 одновременно) делают:**
- механические переносы с **замороженным интерфейсом** («перенеси экран X на сцены, id и
  поведение сохранить; вот команда проверки»);
- независимые проверки («прочитай только эти файлы и ответь на вопросы с цитатами»);
- разведку/research («как устроен протокол X», «какие у SDK ограничения», «собери метрики»).

**Детям нельзя:**
- принимать решения критического пути;
- коммитить;
- прогонять и трактовать негативные проверки (это делает родитель);
- задавать вопросы владельцу (у них нет канала);
- «попутно улучшать» — только заказанное.

**Отчёт ребёнка = самоотчёт.** Родитель обязан повторить ключевой прогон ребёнка до коммита.
Правило провала: **два провала ребёнка на одной задаче — родитель делает сам.**

## 2. Старт сессии: первые 10–15 минут (чеклист)

1. **Загрузить память проекта** (скилл/инструкции) — там ловушки окружения, которые дороже
   всего стоят при повторном открытии.
2. **Прочитать единственный план** и убедиться, что каждый путь из него существует (доки
   устают молча).
3. **Снять живые числа**: прогнать оракул/тесты и посмотреть вердикт-строки. Это «земля под
   ногами» и база для отчёта («было → стало»).
4. **Проверить состояние репо**: `git status`; есть ли незакоммиченное у других (параллельная
   сессия/человек); свежи ли артефакты (сборка/кит старше HEAD = владелец тестирует вчерашнее).
5. **Записать план сессии в todo** — по пунктам, с критериями приёмки (не «сделать UI», а
   «консоль в один ряд: доска ≥ 600px, имена клеток видны — проверка X»).
6. **Оценить бюджет**: сколько прогонов терпит машина; где watchdogs; что делаем, если ребёнок
   не вернётся (тайм-аут, потом родитель).

---

## 3. Формула заказа: без неё не начинать

Каждая единица работы описывается **до** старта:

```
Обещание:   что увидит/получит пользователь (одно предложение)
Сценарий:   одна команда → вердикт строкой → ≤N минут, на релизной сборке
Негатив:    как я сломаю это специально, чтобы чек покраснел ровно тут
Границы:    что НЕ входит (чтобы не «доработать попутно»)
Артефакт:   где лежит доказательство (лог, дамп, отчёт)
```

Пример из NPT (S3): «зрителю с телефона видно картинку стрима» → `scenario_s3.sh` печатает
вердикт строкой → негатив: вернуть старый кегль → падает ровно этот сценарий → границы:
играть с телефона по-прежнему не обещаем.

Если заказ не сводится к этой таблице — он ещё не понят. Вернись к владельцу с вопросом.

## 4. Волны: как раскладывать работу

- **Волна 0 — разведка (родитель сам, 10–15 мин).** Цензус/аудит: `git`-история, дерево, живые
  прогоны. Результат: список фактов и 3–7 гипотез о проблемах, **с числами**.
- **Волна 1 — независимые куски (дети, 2 параллельно).** Каждый кусок — с замороженным
  интерфейсом и своей командой проверки. Пока дети работают, родитель делает своё: то, что
  нельзя делегировать.
- **Волна 2 — связки и интеграция (родитель).** Собрать результат детей, прогнать сквозь
  оракул, починить стыки. Дети здесь — только на «прочитать и сказать, где стык не сходится».
- **Волна 3 — верификация (родитель + слепой ребёнок).** Слепой ребёнок получает только
  артефакт и отвечает на вопросы — так проверяется, что артефакт самодостаточен
  (пример NPT: два слепых ревьюера ответили на 8 и 6 вопросов, тайминги совпали до миллисекунды,
  и один нашёл расхождение, которого ему не показывали).

**Правило волны:** волна заканчивается коммитом и вердиктом. Репо никогда не остаётся красным
на выходе из волны; незавершённое — отдельным флагом в отчёте, а не в красном дереве.

## 5. Промпт ребёнку: шаблон

```
Роль: ты делаешь <одну вещь>. Контекст: <репо, точные пути, где правда>.
Можно трогать: <файлы/каталоги>. Нельзя: <остальное; не коммить; не менять план/доки>.
Команды для проверки: <точные строки>. Вердикт — ТОЛЬКО строкой вывода;
exit code — не вердикт (обёртка возвращает 0 от echo; движок падает при выходе).
Если интерфейс (id/поведение) приходится менять — остановись и напиши об этом.
Отчёт: файлы / команды / вердикт-строки дословно / блокеры. Язык: <...>.
```

Три проверенных типа задач для детей:

1. **Перенос/механика с замороженным интерфейсом** — «экраны в сцены, id и поведение те же;
   прогони <чек>; если чек красный — верни как было и напиши причину».
2. **Research** — «ответь на 5 вопросов, каждый с цитатой из источника; отдельно — что не
   нашлось».
3. **Слепая проверка** — «у тебя только эти файлы; ответь на вопросы; для каждого — цитата;
   если ответа нет, напиши "НЕТ ОТВЕТА" и чего не хватает; не открывай ничего другого».

Пример реального слепого задания (NPT): 4 файла (досье, фильм, 2 дерева) → 8 вопросов →
ответы с цитатами → родитель сверил с эталоном, поймал одну неточность (число из списка
против счётчика) и одно **находкой**: «на доске 0 подписанных клеток в одном состоянии при 40
в другом» — то, чего не видел ни один гейт.

## 6. Дисциплина доказательств (ядро плейбука)

1. **Вердикт — строка**, не код возврата. Форматы бывают разные (`ran N tests, 0 failed`,
   `PASSED/FAILED: причина`, `REPORT DONE`) — матчить по префиксу, а не по одному слову.
2. **Негативная проверка обязательна.** Сломай ровно то, что защищаешь, убедись, что падает
   ровно нужный чек с человекочитаемой причиной, верни — убедись, что зелено. Без этого
   «зелёный» не доказательство. Пример: аудит интерфейса поймал «докторский» дамп по всем
   правилам (5px кегль, вылет за экран, кнопка 18px, доска без имён, консоль 362px).
3. **Не верить**: комментариям («has a consumer» врали), докам (план ссылался на удалённые
   файлы), самоотчётам детей, единственному скриншоту, артефакту старше кода.
4. **Свои прогоны.** Каждое число в отчёте — из прогона этой сессии, желательно твоим
   инструментом, а не пересказом чужого.
5. **Покрытие аудита печатать.** «Проверено 0 проблем» и «не смотрели» должны различаться:
   печатай, сколько файлов/узлов прочитано (`found/kids/dead`).
6. **Не «почини отчёт».** Если инструмент врёт (дамп посреди переразложения дал «на доске нет
   имён»), чини инструмент (ждать стабилизацию раскладки), а не подгоняй вывод.

---

## 7. Неожиданности и конкуренция

- **Параллельная сессия в том же репо.** Коммить часто и малыми диффами, только свои файлы;
  чужие незакоммиченные не трогать; перед правкой общего файла — посмотреть, не переписан ли он.
- **Нашёл баг в чужом коде, который ломает твою задачу** — зафиксировать в отчёте, чинить
  только если без этого задача не проверяется; иначе не расширять радиус.
- **Долгие прогоны** — с `timeout` и watchdog внутри самого инструмента (сценарий печатает
  вердикт, даже если что-то зависло).
- **Ребёнок не вернулся / упал** — тайм-аут, потом повторить с более узкой задачей, потом сам.

---

## 8. Бюджет: контекст, итерации, деньги

- **Контекст родителя — на критический путь.** Механику отдавай детям; читай только то, что
  меняет решение. Большие файлы — частями; не перечитывай то, что уже знаешь.
- **Правило двух итераций.** Не вышло дважды — меняй подход (другая команда, другая
  декомпозиция, делаешь сам), а не повторяй.
- **Инструменты — из того окружения, где они есть.** Пример NPT: `py -3.12` из ядра агента и
  из терминала — РАЗНЫЕ окружения (в ядре нет playwright/Pillow). Тяжёлые прогоны — из
  терминала, файловые операции — из ядра.
- **Нативные бинарники не видят POSIX-пути** (`/c/...`) — передавай нативные (`C:/...`).

---

## 9. Финал сессии: отчёт-доказательство

Обязательный каркас отчёта:

```
1. Что я прогнал (таблица: команда → строка-вердикт дословно)
2. Заказ → результат (по пунктам; где доказательство)
3. Что НЕ проверено — честно (границы)
4. Коммиты: хеш + одна строка
5. Что меняется в плане/доках и что обновлено (в том же коммите)
6. Что нужно от владельца (решения, доступы, «go»)
```

Если сессия чему-то научила (новая ловушка, новый приём) — дописать в скилл/память проекта
**до** конца сессии, а не «потом».

---

## 10. Антипаттерны (проверять в каждой сессии)

1. Метрика-храповик: число тестов/гейтов растёт как показатель прогресса.
2. Второй дом правды (макет, копия токенов, параллельный справочник) + сторож от рассинхрона.
3. Проверки, приколоченные к литералам дизайна: правка продукта = правка проверок.
4. «Зеленеет не то»: гейт отвечает «нарисовано», а нужен «прочитано/играется».
5. Артефакт старше HEAD: владелец щупает вчерашнее.
6. Архив вместо удаления; мёртвые механизмы рядом с живыми.
7. Скрипт-обёртка, игнорирующий аргументы (CI зелёный, а не запускалось ничего).
8. `grep` вердикта без двоеточия ловит информационную строку.
9. Отчёт по памяти: «в прошлый раз было…» — не доказательство.
10. Дети без замороженного интерфейса: «попутно улучшил» = чужая регрессия.
11. Коммит-свалка на 40 файлов: потом невозможно понять, что сломалось.
12. Красное дерево на выходе: следующая сессия начинает с разбора, а не с работы.

## 11. Приложение: рабочие команды и примеры (NPT, 2026-10-16)

```bash
# земля под ногами
bash tools/ci/run_tests.sh            # вердикт: ran N tests, 0 failed → ORACLE PASSED
bash tools/ci/run_probes.sh           # поведенческие пробы
bash tools/ci/gates/read_gate.sh neuro

# паспорт интерфейса (агентские «глаза»): дерево + текстовая карта + кадры + фильм + дифф
bash tools/ci/ui_passport.sh [--film] [--save-baseline] [--diff]
py -3.12 tools/ci/web_passport.py --url=URL --name=home --out=passport --viewport=1440x900
py -3.12 tools/ci/ui_passport_report.py <repo> --dir=passport
py -3.12 tools/ci/ui_passport_diff.py  <repo> --dir=passport

# аудит интерфейса по правилам (UA-01..09), exit 1 при критичном
py -3.12 tools/ci/ui_audit.py <passport-dir>
```

Пример негативной проверки (проверено): аудит на «докторском» дампе →
`PROBLEM C UA-01 … доска без имён`, `PROBLEM C UA-02 … консоль 362px (40%), доска 450px (50%)`,
`==> UI AUDIT: 7 problems (C 2, W 5)` → `exit 1`; на чистом — ноль.

Пример находки, которую дала верификация артефакта (а не код): в трёх состояниях решения
человека консоль занимает 362px, кнопки встают колонкой, доска падает до 450px, и собственный
шаг 3 дизайна прячет имена клеток — при **зелёных** READ-01/02/03, потому что у них нет правила
про высоту консоли. Это ровно та работа, которую должна находить одна сессия с субагентами:
измерить, назвать числами, предложить решение — и оставить владельцу решение, а не догадку.

## 12. Мини-контрольный лист перед «готово»

- [ ] Вердикты — строками, из прогонов этой сессии.
- [ ] Негативные проверки прогнаны и записаны.
- [ ] Артефакты свежее HEAD; отчёт не ссылается на старое.
- [ ] Дети: ключевые результаты перепроверены родителем.
- [ ] Коммиты малы и описаны; дерево чистое (или явно сказано, что грязное и почему).
- [ ] План/снимок/скилл обновлены в том же коммите, что и работа.
- [ ] В отчёте есть список «что НЕ проверено».
