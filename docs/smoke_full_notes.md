# Полный смоук всего приложения — заметки разведки

Артефакт этапа 0 перед написанием `tools/smoke_full.gd`. Здесь только **факты,
проверенные по коду**, а не предположения: от них зависит сценарий прогона.

## Роли и транспорты: что есть сейчас

| № | Вопрос | Ответ | Где проверено |

**Вывод.** Браузерного игрока в окончательной реализации **пока нет вообще** —
это осознанное решение (`docs/plan.md`, «Up next» §3: только после стабилизации
UI). Поэтому «заходят игроки из браузера» сейчас проверять не на чем.

## Что это значит для сценария

Шаги владельца раскладываются так:

| Шаг | Чем проверяется |
|---|---|
| запускается окно | процесс A `--admin`, процесс B `--stream` |
| включается «стрим» | **второй процесс того же бинарника** с `--stream` (этап 7: роль выбирается при запуске, не кнопкой) |
| собирается лобби, настройки, старт | `SettingsOverlay` программно |
| админ правит параметры игрока | `AdminController` + `push_intent` |
| идёт игра, все события | полный проход до `game_over` |
| статистика | `smoke_full_report.json` |
| **браузер, игроки заходят** | требует транспорта, которого нет → этап 1 (WS-сервер) |

## Решение по сети

Чтобы «браузер заходит» проверялось **по-настоящему**, а не подменялось третьим
локальным окном, добавляется минимальный WS-сервер (этап 1) и драйвер `REMOTE`
на клиенте (этап 2). Тогда окончательная реализация не расходится с тем, что
тестировалось.

Схема: **один хост, два канала на игрока**

- `spectator` — общая рассылка, без `private` и без `legal_actions`;
- `seat/<token>` — персональный канал владельца места, с его приватной секцией.

Два канала, а не один, — это **структурная** защита spectator-safe: утечка
приватного в общий канал невозможна по построению, а не по проверке.

Клиент шлёт **только интенты**, хост валидирует через `push_intent` и рассылает
результат. Состояние живёт исключительно в движке (детерминизм по seed).

## Ограничения, которые смоук не закроет

- **Живой Twitch** — реального чата нет; проверяется, что `ChatPoll` **скрыт**
  без данных (уже покрыто).
- **Реальный OBS** — проверяется spectator-safe картинка stream-окна; захват
  OBS — вручную.
- **Живой Neuro SDK** — в headless нет `NEURO_SDK_WS_URL`, SDK-места уходят в
  AI-fallback; живое соединение — отдельно (`docs/plan.md` §2).
- **WebGL под SwiftShader** — известная нестабильная среда для захвата кадров
  (предупреждение в `.github/workflows/web-export.yml`). Если браузерный шаг не
  пойдёт — он остаётся ручным, остальные шаги прогоняются.

## Порядок этапов

0. эта заметка
1. WS-сервер `server/game_server.gd`: spectator + seat-каналы, `projection` /
   `delta` / `event` / `intent` / `reject`, реконнект по токену
2. драйвер `REMOTE` (клиент `WebSocketPeer` → `push_intent`), встроить в
   `resolve_driver`
3. оркестратор `tools/smoke_full.gd`: поднять admin + stream + server
4. реальный браузер (headless Chrome через CDP): WebUI, посадка за место, ход
5. полный проход: лобби → настройки → админ-правки → партия → аукцион → торг →
   game-over
6. ассерты: `spectator_leaks=0`, `raw_tags=0`, `modal_stacks≤1`, покрытие событий
7. `smoke_full_report.json` + скриншоты 3 окон × фазы
8. хвосты: WCAG в WebGL, пул `EffectLayer`
